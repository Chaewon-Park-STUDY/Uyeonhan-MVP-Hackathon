# 우연한 식탁 MVP — 설계서 (v0.2)

> 작성: 박채원 · 2026-10-17 · 상태: v0.2 (Blaybus FAQ 반영)

---

## 1. 목적

**1순위: 운영자의 수작업 제거.** 신청 확인, 입금 확인, 수기 매칭, 단체방 생성, 리마인드 발송을 자동화해 정상 흐름은 운영자 개입 없이 끝나고, 운영자는 예외만 처리한다.

**2순위: 매칭 품질의 지속적 개선.** 피드백이 쌓일수록 "좋은 테이블"의 기준을 스스로 학습하는 매칭 엔진.

**차별화:** 운영자의 경험을 사전분포로 시작해, 회차마다 탐색과 활용의 균형을 잡으며 학습하는 **베이지안 밴딧 매칭 엔진**.

## 4. 매칭 엔진

### 4.1 조건 구분

| 구분 | 조건 | 처리 |
|---|---|---|
| 필수 | 결제 완료, 날짜·지역 일치, 4~6명, 최고·최저 나이 차이 ≤ 8, 차단·신고·비선호 관계 없음 | 위반 시 확정 불가 → 재배치 |
| 선호 | 성비, MBTI, 관심사, 희망 성향, 새로운 사람 | 점수화 후 최적화 |

### 4.2 선호 조건 점수 φ(T) ∈ [0,1]⁵

테이블 T (인원 n)에 대해:

| 항목 | 정의 |
|---|---|
| 성비 φ₁ | m = min(남, 여). m ≥ 2이면 `1 − |남−여|/n`, m = 1이면 0, m = 0(동성)이면 0.3 |
| MBTI φ₂ | `1 − |E 인원 − I 인원| / n` |
| 관심사 φ₃ | 테이블 내 모든 참가자 쌍의 관심사 Jaccard 유사도 평균 |
| 희망 성향 φ₄ | 각 참가자가 원한 성향 중, 다른 멤버 1명 이상이 충족하는 비율의 평균 (대응표 4.3) |
| 새로운 사람 φ₅ | `1 − (이전에 만난 쌍 수 / 전체 쌍 수)` |

### 4.3 희망 성향 대응표

| 만나고 싶은 사람 | 충족 조건 (상대의 "나는 어떤 사람") |
|---|---|
| 편하고 유머 있는 사람 | 가볍고 유머 있는 대화를 좋아함 |
| 잔잔하고 안정적인 사람 | 잔잔하고 조용한 편 또는 경청을 잘 함 |
| 깊은 대화가 되는 사람 | 깊은 대화를 좋아함 |
| 열정 있는 사람 | 활기차고 에너지 있는 편 또는 이야기를 이끄는 편 |
| 나와 비슷한 사람 | 성향+관심사 Jaccard ≥ 0.4 |
| 나와 다른 자극을 주는 사람 | 성향+관심사 Jaccard ≤ 0.2 |

### 4.4 v1 — 규칙 기반 점수 (콜드 스타트)

```
score(T) = wᵀ φ(T),   w = (0.30, 0.25, 0.20, 0.15, 0.10)
```

### 4.5 v2 — 베이지안 업데이트

테이블 만족도 y_T (참가자 테이블 점수 1~5의 평균)를 선형 모형으로 둔다.

```
y_T = β₀ + βᵀ φ(T) + ε,      ε ~ N(0, σ²)
```

**사전분포 (Normal–Inverse-Gamma, 켤레)**

```
σ² ~ IG(a₀, b₀)
(β₀, β) | σ² ~ N(μ₀, σ² Λ₀⁻¹)
μ₀ = (3, 2w)          ← 운영자 가중치를 1~5점 척도로 옮긴 값
```

**사후분포 (닫힌 형태)**

```
Λₙ = Λ₀ + XᵀX
μₙ = Λₙ⁻¹ (Λ₀ μ₀ + Xᵀ y)
aₙ = a₀ + N/2
bₙ = b₀ + ½ (yᵀy + μ₀ᵀ Λ₀ μ₀ − μₙᵀ Λₙ μₙ)
```

- X: 지금까지 확정·피드백 완료된 테이블들의 [1, φ(T)] 행렬, N: 테이블 수
- MCMC 없이 numpy로 계산, 매 회차 피드백 마감 후 `/api/learn`이 갱신해 `model_snapshots`에 저장
- 피드백이 적으면 사전분포(운영자 경험)가 지배하고, 쌓일수록 데이터가 지배

### 4.6 v3 — Thompson Sampling (밴딧 강화학습)

| 강화학습 요소 | 정의 |
|---|---|
| 상태 | 이번 회차 신청자 풀 + 현재 사후분포 |
| 행동 | 신청자를 4~6인 테이블로 나누는 배치 |
| 보상 | 식사 후 테이블 만족도 y_T |
| 정책 | Thompson Sampling |

```
매 회차:
  1. σ̃² ~ IG(aₙ, bₙ),  β̃ ~ N(μₙ, σ̃² Λₙ⁻¹)
  2. β̃ 로 Σ_T β̃ᵀ φ(T) 를 최대화하는 배치 탐색 (4.7)
  3. 식사 후 피드백 y_T 수집
  4. 사후분포 갱신 (4.5)
```

- 불확실한 항목일수록 사후분포가 넓어 자연스럽게 더 탐색하고, 확실해지면 활용으로 수렴
- **안전장치:** 필수 조건은 탐색 대상이 아니다. 확정 여부는 샘플 β̃가 아니라 **사후평균 μₙ 기준 최소 점수**로 판단해, 탐색 때문에 품질이 바닥 아래로 내려가지 않게 한다.

### 4.7 배치 알고리즘

회차(날짜·지역)별 후보 풀에 대해:

1. **후보군:** 결제 완료 + 해당 회차 선택자 (SQL)
2. **초기 배치:** 나이순 정렬 후 그리디로 4~6인 묶음 생성 (나이 차이 8살 제약을 먼저 만족)
3. **개선:** 두 테이블 간 참가자 맞바꾸기·이동을 점수 합이 오르는 동안 반복 (local search). 필수 조건 위반 이동은 금지
4. **분리·병합:** 7명 이상은 분리, 합쳐서 4~6명이 되는 미완성 테이블은 병합
5. **재배치 (PRD 7.4 순서):** 같은 날짜·같은 지역 → 같은 날짜·다른 희망 지역 → 다른 날짜·같은 지역 → 다른 날짜·다른 지역
6. **확정:** 필수 조건 충족 + 사후평균 점수 ≥ 최소 점수 → 자동 확정 (DB 트리거가 재검증)
7. **실패:** 남은 참가자는 `ALTERNATIVE_OFFERED` → 신청 시 미리 고른 선택지 적용, 버튼으로 변경 가능
8. **설명 저장:** 테이블별 항목 점수, 재배치 횟수, 배치 사유 (참가자에게는 상세 점수·타인 개인정보 비공개)

**실행 시각:** 매칭 마감 = 환불 마감 = **화요일 24:00** (목요일 모임 기준). 환불이 끝난 시점에 매칭해야 확정 후 취소로 테이블이 깨질 위험이 최소화된다.

### 4.7.1 확정 후 결원 처리 (FAQ Q6, 직접 정한 규칙)

확정 테이블에서 취소가 생겨 3명 이하가 되면:
1. 같은 회차의 미배치 대기자 중 필수 조건을 만족하는 사람으로 충원 (점수 최대)
2. 충원 불가 시, 남은 인원을 같은 회차의 다른 확정 테이블(6명 미만)에 넣어 필수 조건 재검증 후 이동
3. 그래도 불가하면 남은 인원에게 `ALTERNATIVE_OFFERED` → 신청 시 고른 선택지 적용 (필수 조건은 완화하지 않음, 일정 이동·환불은 참가자가 선택)
4. 결원 원인 제공자가 아닌 참가자에게는 환불 100% (멤버십은 기간 연장)

### 4.8 검증 (시뮬레이션)

가상데이터에는 결과값(만족도)이 없으므로 시뮬레이션으로 검증한다.

1. 사전분포와 **다른** 참값 β*를 설정 (예: 실제로는 관심사가 MBTI보다 중요)
2. 회차마다 신청자를 재표집하고, 선택된 배치에 대해 `y_T = β*ᵀφ(T) + ε` 생성
3. 비교: 그리디(사후평균만 사용) vs Thompson Sampling, 30회차
4. 지표
   - 누적 후회: `R_t = Σ (최적 배치의 β*ᵀφ 합 − 선택 배치의 β*ᵀφ 합)`
   - 사후평균 μₙ이 β*로 수렴하는 과정
5. 결과 그래프를 어드민 "학습 현황" 화면에 표시

## 6. 참가자 입력 항목

- 기본: 이름, 연락처, 출생연도, 성별, 직업
- 매칭: MBTI, 관심사, 나는 어떤 사람, 만나고 싶은 사람
- 식사: **알레르기**(식당 배정 시 필수 제외), **비선호 음식**(식당 배정 시 감점), 가격대
- 신청: 회차(날짜·지역) 복수 선택, 이용권, 매칭 실패 시 선택지, 추천인 코드

지역: 홍대/합정 · 강남/신논현 · 을지로/종로 · 잠실 (선택형, 현재 운영 지역만. FAQ Q9)

식당: 리뷰 평점이 좋고 예약 가능한 곳을 우선 배정 (FAQ Q9)

## 7. 자동화 흐름

```
신청 → 모의 결제(PAID 자동 전환) → [마감 시각, pg_cron] 자동 매칭
→ 자동 확정 → 식당 자동 배정(알레르기 제외) → 단체방 생성 + 안내 게시
→ [1일 전] 리마인드 → [시작 시각] 대화 주제 게시(Gemini, 실패 시 템플릿)
→ 체크인 → 피드백 → 쿠폰 지급 + 다음 일정 추천 → [피드백 마감] 모델 학습
```

운영자 사전 검토 없이 자동 확정 (FAQ Q10). 운영자 화면에는 결제 오류, 식당 부족, 해결 안 된 조건 충돌, 알림 실패, 신고만 표시.

## 10. 참고: 운영 로그 미제공에 따른 검증 방식

문의·운영 로그는 제공되지 않는다 (FAQ Q11). 따라서 매칭 품질 학습은 4.8의 시뮬레이션으로 검증하고, 실제 운영 시 피드백이 쌓이면 같은 코드가 그대로 실데이터로 학습한다.
